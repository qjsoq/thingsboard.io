## The wall we could see coming

A customer came to us with a fleet that was about to grow more than seven times bigger. They already had almost 700,000 devices in production, and they planned to reach five million within a few months. Many of the new devices were cameras, which send far more data per device than a typical sensor. They could not move the deadline, and the fleet kept growing while we worked.

On paper, ThingsBoard is purpose-built for horizontal scalability. Scaling device connectivity is a matter of provisioning additional transport nodes, while telemetry growth is handled by expanding the time-series database cluster. Every layer of the platform scales out seamlessly by adding machines — an approach that has proven reliable for years.

Every layer except one. The relational database at the centre of the platform grows in a different direction — upwards. A bigger instance, faster disks, another round of tuning.

A larger instance with faster storage carries more load. The gains come in fixed steps, each costing more than the last while adding less throughput. The steps end because there is a largest machine on offer and nothing beyond it, so a bigger machine raises the limit without removing it.

So we set out to change the game. What we needed was a relational database that grows by adding servers rather than by replacing them, in time for a deadline that could not move.

## What actually gets hot

<img src="/images/blog/scaling-postgresql-horizontally-with-citus-for-millions-of-iot-devices/what-actually-gets-hot.svg" alt="ThingsBoard architecture with one PostgreSQL server: devices connect through MQTT, HTTP, CoAP and LwM2M transports, telemetry history goes to Cassandra at normal load, and every attribute and latest-value update funnels into PostgreSQL, which runs hot with its write capacity saturated" style={{margin:'16px auto'}} />

Telemetry history is the obvious suspect, and it can be heavy, but it is the easy part to spread over many servers. Large deployments usually keep it in Cassandra, which is built to do exactly that.

The pressure comes from a much smaller set of data: each device's attributes and its latest telemetry value for every key. Unlike history, these are never appended. ThingsBoard holds a single value per device and key in PostgreSQL — battery level, temperature, location — and each telemetry message the device sends overwrites the value already there. Five million devices do not make these tables enormous. They make them extraordinarily busy.

That property decides whether a table can be spread across servers. Every telemetry message adds a new record to history, so no two writes ever target the same one: Cassandra places them by partition key across the cluster, and none of them waits on another. Latest values work the other way round. Each write targets a record that already exists, so it has to reach the server holding that record — and with a single PostgreSQL instance, that is the same server for all five million devices.

The volume grows faster than the message count suggests. A smart meter sending three telemetry keys in one message produces three row updates rather than one, and an industrial controller reporting ten keys produces ten. Every one of those updates has to be applied, because dashboards, alarm rules, calculated fields and entity data queries all read the latest values and depend on them being current.

## Why a bigger machine isn't the same as more machines

Before distributing anything, we worked through the standard ways of making a single PostgreSQL instance carry more load.

- **Partitioning** splits a table into smaller segments on the same machine. Queries scan less, and the server still performs every write itself.
- **Data retention** removes old records. The latest-value table keeps exactly one row per device and key, so there is nothing in it to expire.
- **Replication** keeps a standby copy of the database on another server, which protects you against losing the primary one.

A larger instance is the one remedy that genuinely raises write throughput, since the same server gets through the same updates faster. Horizontal scaling splits those updates across several servers instead. The difference shows up as more devices are provisioned. Doubling the device count doubles the updates arriving every second, and only spreading the writes lets you keep up by adding hardware rather than replacing it.

Which resource gives out first depends on the deployment. In write-heavy installations it is often storage, because every change has to be recorded durably before the platform confirms it, and a cloud storage volume is provisioned with a limit on how many read and write operations it can perform each second, a figure known as IOPS. It can equally be processing power. Either way, buying more of it for one machine is a different move from spreading the writes over several, and only the second keeps pace with a fleet that keeps expanding.

## The solution

<img src="/images/blog/scaling-postgresql-horizontally-with-citus-for-millions-of-iot-devices/the-solution.svg" alt="The same architecture with PostgreSQL replaced by a Citus cluster: ThingsBoard writes attributes and latest values straight to four workers, each at normal load, while the coordinator stays off the write path" style={{margin:'16px auto'}} />

The requirement was a relational database that absorbs more writes when you add servers, without giving up SQL or transactional correctness, and one that installations already in production could move to without being rebuilt around it. That second condition carried most of the weight. Changing the database engine means reworking the schema, the application layer, the backup procedure and the monitoring, then repeating that work in every self-hosted deployment, and here it would have run against a fleet that was already growing and a date that could not move. What we needed was a way to spread the writes that stayed inside PostgreSQL itself.

[Citus](https://www.citusdata.com/) is an open-source extension that turns a group of PostgreSQL servers into one distributed database. It isn't a fork of PostgreSQL and it isn't a separate engine — it installs into a standard PostgreSQL instance like any other extension. The project started at Citus Data in 2010, was open-sourced in 2016, and was acquired by Microsoft in 2019. Also, the same technology powers Microsoft's own distributed PostgreSQL service named Azure Cosmos DB for PostgreSQL. Since 2022 every part of Citus is open source. That includes the shard rebalancer, which moves data onto a newly added server, and until then the free version could only do that by pausing writes to the tables being moved.

A Citus cluster has one coordinator node and any number of worker nodes, and every table belongs to one of three categories.

- **Distributed tables** are split into shards by hashing a chosen column, and those shards are spread across the workers.
- **Reference tables** are copied in full to every worker, so a lookup against one is answered locally.
- **Local tables** stay on the coordinator.

Choosing a category for each table was the largest part of the integration work, though not the whole of it. Existing queries kept working, because a Citus cluster speaks the same protocol as a standard PostgreSQL server and works with the same drivers and the same SQL, so the application layer did not have to be rebuilt around a new database. Underneath, some keys and constraints in the schema were reworked around the column that decides which worker a row lives on. ThingsBoard now groups writes so that each batch goes to a single worker, and it holds a pool of connections to every worker rather than one pool to a single server. Running the database is different work once it is a cluster. The coordinator and every worker are backed up together and have to be restored together, and monitoring has to cover all of those machines instead of one. The platform itself works exactly as it did before, and that is what settled the choice.

## One device, one worker

Which category a table falls into comes down to how closely it belongs to a device.

The tables that grow as devices are provisioned are spread across the workers. Those are a device's own record, its attributes, its latest value for every telemetry key it reports, and any alarms raised on it. Other entity types that carry their own attributes and telemetry are placed the same way, so each one lands on a single worker together with its data.

The tables that almost every query reads and that barely grow with the fleet are copied to every worker instead. A deployment with five million devices has no more device profiles than one with a thousand, so a full copy on each worker costs very little.

The remaining tables stay on the coordinator, exactly where they were before.

## Choosing a connection mode

Integrating ThingsBoard with a Citus cluster generally follows one of two patterns. The fundamental distinction lies in query routing: who makes the split-second decision on where each write target is located?

In **coordinator mode** every statement is sent to the coordinator, which looks up the worker that owns the row and passes the statement on. Nothing in the application has to know that a cluster is there, which makes this the simplest way to run, and it already spreads the write load across all of the worker disks. The cost is that every connection and every query plan passes through one machine, so at high throughput the coordinator begins to limit the cluster the same way a single server did.

<img src="/images/blog/scaling-postgresql-horizontally-with-citus-for-millions-of-iot-devices/coordinator-mode.webp" alt="Coordinator mode: ThingsBoard sends every statement to the Citus coordinator, which forwards it to the owning worker" style={{width:'85%',height:'auto',margin:'16px auto'}} />

**The other mode is smart routing,** where ThingsBoard keeps the routing decision to itself. A device's attributes and latest telemetry values live on one Citus worker, so that is where ThingsBoard sends them, with nothing in between. The coordinator is still there for schema changes, for the tables that stayed on it, and for the occasional query that has to reach across workers, and the stream of latest-value updates arriving every second no longer passes through it.

Smart routing is on by default whenever Citus is enabled, since it is the mode that takes the most writes per second.

<img src="/images/blog/scaling-postgresql-horizontally-with-citus-for-millions-of-iot-devices/smart-routing.webp" alt="Smart routing: ThingsBoard keeps a connection pool per worker and writes attributes and latest values straight to it, with the coordinator off the write path" style={{width:'85%',height:'auto',margin:'16px auto'}} />

## The benchmark setup

The benchmark exists to show what changes when several servers share the relational write load instead of one, so we sized the traffic past what a single instance handles comfortably. The fleet is the size the customer is heading for, five million provisioned devices, with a million of them reporting telemetry throughout the run.

Test configuration:

- 4 Citus worker nodes, 1 coordinator and 6 ThingsBoard nodes, each on its own virtual machine
- 32 shards spread across the 4 workers, 8 on each
- 5,000,000 provisioned devices, of which 1,000,000 published over MQTT for the whole run
- Three device profiles: 340,000 smart meters, 340,000 smart trackers and 320,000 industrial controllers
- 60 load generators, each raising one alarm a second alongside the telemetry

The devices were split across three profiles rather than one, because the number of telemetry keys in a message decides how many rows that message updates, and a real fleet is never uniform:

| Device profile | Active devices | Telemetry keys per message | Publish interval per device | Messages/s | `ts_kv_latest` rows/s |
| --- | --- | --- | --- | --- | --- |
| Smart meter | 340,000 | 3 | 20 s | 17,000 | 51,000 |
| Smart tracker | 340,000 | 5 | 40 s | 8,500 | 42,500 |
| Industrial controller | 320,000 | 10 | 80 s | 4,000 | 40,000 |
| **Total** | **1,000,000** | — | — | **29,500** | **133,500** |

We provisioned all five million devices even though only a million of them ever published. The million publishing devices set the write load, and the four million idle ones kept the tables at production size, because every write has to find its row in a much bigger index and a run against a million rows would have told us nothing about what the customer was going to live with.

<img src="/images/blog/scaling-postgresql-horizontally-with-citus-for-millions-of-iot-devices/provisioned-devices.webp" alt="ThingsBoard device counters: 4,000,000 inactive, 1,000,000 active, 5,000,000 total" style={{margin:'16px auto'}} />

The message rate understates the work. About 30 thousand messages a second arrive, and they carry more than 133k telemetry keys between them, each one overwriting a value of its own, so that is how many row updates a second the database has to keep up with. Both the single instance and the four-worker cluster were given the same load.

## Single instance vs. cluster

To see what distribution changes on its own, we ran the same load twice, once against a single PostgreSQL instance and once against the four-worker cluster. Every database node had a virtual machine to itself, an AWS c6a.4xlarge with 16 vCPUs and 32 GB of memory, whether it was the single instance, the coordinator or one of the four workers. Both runs started from the same 200 GB of data and indexes, with all five million devices provisioned, and used the same database tuning and the same ThingsBoard configuration apart from the Citus settings.

We wrote a small <a href="/resources/blog/pg-queue-vs-throughput.sql" download="pg-queue-vs-throughput.sql">**script**</a> that samples the database 120 times, a second apart, and records how much it wrote between one sample and the next. At any moment some of its connections are writing while others wait their turn, so the script grouped those seconds by how many were waiting. While fewer than half were waiting, the database wrote between 63,269 and 64,116 rows a second, and it spent 31 of the sampled seconds in that state. The rate fell to 56,386 once more than half were waiting, and to 29,092 once more than three quarters were, which is where it stayed for 77 of the 119 seconds.

The single instance used 3 to 6 of its 16 cores for the whole run, and its memory and its IOPS stayed below their limits too. No resource on the machine was saturated, so what held the write rate down was inside PostgreSQL rather than in the hardware underneath it.

<img src="/images/blog/scaling-postgresql-horizontally-with-citus-for-millions-of-iot-devices/single-instance-cpu.webp" alt="Single PostgreSQL instance CPU usage between 3 and 6 cores during the run" style={{margin:'16px auto'}} />

The four-worker cluster took the same 133,500 latest-value updates a second and kept up with them. Each worker wrote between 30,000 and 35,000 rows a second, more than 134,000 between them. That figure counts every row the workers wrote, the values being overwritten and the rows being written for the first time, so it covers the whole relational write load rather than the latest values alone. The coordinator wrote almost nothing, because ThingsBoard sends every latest-value update straight to the worker that holds the device.

<img src="/images/blog/scaling-postgresql-horizontally-with-citus-for-millions-of-iot-devices/cluster-rows-written.webp" alt="Rows written per second on each Citus node: workers steady at 30,000 to 35,000, coordinator near zero" style={{margin:'16px auto'}} />

The same script run against the cluster explains why. Fewer than a quarter of its connections were waiting at any point across the 146 seconds it covered, so it never reached the state the single instance spent most of its time in. That run spans more seconds than the single instance run because every sample has to reach all four workers before the next one starts. Each worker owns an even share of the devices and takes the same share of the updates, which with four workers is about a quarter each. Connections that would have queued behind one another on one server are now spread across four machines that never wait on each other.

<img src="/images/blog/scaling-postgresql-horizontally-with-citus-for-millions-of-iot-devices/cluster-lock-wait.webp" alt="Citus cluster: all 146 sampled seconds under 25% lock-wait share at 134,258 rows/s" style={{margin:'16px auto'}} />

The platform side agrees. Every buffer on the ThingsBoard nodes reported a size of zero, saving as many updates as arrived with none failed, which is what keeping up looks like from the outside.

<img src="/images/blog/scaling-postgresql-horizontally-with-citus-for-millions-of-iot-devices/cluster-write-queues.webp" alt="ThingsBoard latest-value write queues during the cluster run, all at queue size zero with no failures" style={{margin:'16px auto'}} />

Each worker used about 8 of its 16 cores and the coordinator about 6. The cluster took everything the load offered, with fewer than a quarter of its connections waiting where the single instance had more than three quarters.

<img src="/images/blog/scaling-postgresql-horizontally-with-citus-for-millions-of-iot-devices/cluster-cpu.webp" alt="CPU usage per Citus node: workers around 8 cores, coordinator around 6" style={{margin:'16px auto'}} />

## What are the honest pros and cons of this setup

Running PostgreSQL as a cluster changes what a ThingsBoard deployment can grow into. Write capacity stops being a property of a single machine and becomes something you extend by adding servers, and the relational database turns into a group of machines that are sized and operated as one system. That difference is where a cluster's strengths come from, and where its costs come from too.

### Pros

- **Cheaper storage.** Writes are divided between the workers, so each machine needs a disk sized for the share of the data it holds rather than for the whole deployment. The fast, expensive volume that a single server depends on stops being a requirement.
- **Capacity you add instead of buy.** Write throughput grows with the number of workers rather than with the price of one machine. You add a worker, move part of the data onto it, and repeat that step the next time the fleet grows.
- **A smaller blast radius.** Each worker holds only the data assigned to it, so losing one leaves everything on the other workers readable and writable. A worker is an ordinary PostgreSQL server, so it can run with a standby of its own and be promoted in place.
- **Backups that are no longer one big job.** Every node saves its own share at the same time as the others, so the largest tables are never written out or reloaded by a single server.

### Cons

- **More processor time overall.** A cluster gets through the same writes using more processor time than one server would, because every node runs a database of its own and any work spanning several nodes has to be planned and combined across them. Cheaper disks on each worker take one cost down and this takes another one up, so some of what a cluster saves on storage comes back as processor cost.
- **More moving parts to run.** A cluster is more machines to pay for, patch, back up and monitor, and it gives you more places where something can go wrong. Capacity planning covers every node rather than one.
- **Queries that span the fleet cost more.** A lookup for a single device is answered by the worker holding it, while a query reaching across many devices has to be run on several workers and assembled from their results, which is more work than the same query on one server.
- **Decisions made up front.** The number of shards is fixed when the tables are distributed, and it has to be set high enough for the largest number of workers you expect to run, so a cluster is planned around the fleet it will reach rather than the one it starts with.

## Conclusion

ThingsBoard 4.3 LTS can spread its relational database across several servers instead of keeping it on one. Each device's writes go to one of those servers instead of all of them arriving at the same one. Nothing changes for the people using the system, because dashboards, rule chains and integrations work exactly as before.

That closes the last gap in the architecture. The rest of the platform has always grown by adding machines, and now the database grows the same way.

A cluster is more to run than a single server, so it is worth choosing deliberately. A well-tuned single database with room to spare is still the simpler answer, and the case for a cluster begins when the write load outgrows it.
